# Паспорт флагманской инициативы: приоритизация подозрительных операций

Статус: эталонная проработка для ревью глубины. Разделы 3–5 продолжены в `Task2/flagship-passport.md`.

## 0. Канвас оценки инициативы

| Критерий | Оценка | Основание |
|---|---|---|

## 1. Оценка инициативы

**Вердикт: гибрид.**

ML нужен для ранжирования операций по признакам поведения, связей и свободного текста. Правила внутреннего контроля, обязательная фиксация, маршрутизация и решение сотрудника остаются вне модели. Внешняя платформа «Знай своего клиента» даёт только вспомогательный сигнал; банк самостоятельно проводит итоговую оценку.

**Граница постановки:** сервис не выдаёт заключение «схема / не схема», не отменяет операцию и не заменяет расследование. Он только меняет порядок разбора уже помеченных операций.

## 2. Постановка

### 2.1. Бизнес-проблема и текущий процесс

Пороговые правила и внешние сигналы помечают около 35 тыс. операций в месяц. Служба из 25 сотрудников разбирает около 10 тыс., в среднем по 12 минут; приоритет отдаётся крупным суммам. Около 4% разобранных операций эскалируются, но эскалация не равна подтверждённой схеме.

Целевое изменение — помочь сотруднику раньше увидеть операции с высокой экспертной приоритетностью и сократить время на первичный разбор, сохранив действующие обязательные проверки.

### 2.2. Операция и модальность

| Параметр | Решение |
|---|---|
| Единица обработки | Одна помеченная операция на момент постановки в очередь финмониторинга. |
| Режим | Асинхронная пакетная обработка новых помеченных операций с перестроением приоритетной очереди; срочные обязательные сигналы не ждут пакета. |
| Табличные признаки | Сумма, дата, канал, ОКВЭД, контрагент, лимиты, отклонения от истории клиента, частота и дробление. |
| Текст | Назначение платежа в свободной форме; используется как дополнительный источник признаков, а не как основание для автоматического решения. |
| Связи | Агрегированные признаки клиент–контрагент и транзитные цепочки за ограниченное окно; графовая нейросеть не требуется. |
| Временная граница | Все признаки формируются только из данных, доступных до момента скоринга, чтобы исключить утечку будущего. |

### 2.3. Выход модели и бизнес-выход

| Уровень | Содержимое |
|---|---|
| Модель | Ранжирующая оценка экспертной приоритетности операции относительно других операций в очереди. Это не вероятность мошенничества и не вероятность подтверждённой схемы. |
| Сервис | `operation_id`, `priority_score`, `priority_band`, `reason_codes`, `model_version`, `feature_snapshot_id`, `scored_at`, `fallback_code`. Обязательные сигналы правил передаются отдельно и не перезаписываются моделью. |
| Бизнес | Порядок операции в существующей очереди и объяснение для сотрудника. Сотрудник выполняет разбор, эскалацию и другие действия по действующему регламенту. |

Модельный score нельзя интерпретировать как доказательство схемы. Никакое действие, затрагивающее клиента, не выполняется только на его основании.

### 2.4. Источник правильного ответа

Для обучения приоритизации используется **экспертная ординальная метка приоритетности разбора** по заранее утверждённому гайдлайну: «низкий / средний / высокий». Эксперт оценивает операцию и доступный контекст, не зная score модели.

Дополнительно, но отдельно сохраняются:

- факт эскалации на углублённое расследование;
- исход расследования;
- формально подтверждённый случай;
- срабатывания правил и внешние сигналы.

Эти поля не объединяются в одну метку. Эскалация не считается подтверждением схемы, а отсутствие прошлой проверки не считается чистым исходом.

### 2.5. Программа получения сигнала

1. Случайная стратифицированная выборка помеченных операций по сегментам, суммам, каналам и признаку прошлого разбора — для несмещённой оценки потока.
2. Обогащённая выборка редких и сложных сценариев — для обучения и проверки важного класса; её доля отдельно учитывается при оценке метрик.
3. Разметка двумя экспертами не менее чем для 20% выборки; расхождения разрешаются по гайдлайну и используются для оценки согласованности.
4. В эксплуатации разметка поступает и из приоритетной очереди, и из постоянной вероятностной контрольной выборки. Обучение только на отобранных моделью операциях запрещено.

### 2.6. Критерии полезности

- Качество верхней части очереди не ниже текущего подхода, а целевое улучшение проверяется на отложенной и контрольной выборках.
- Среднее и 95-перцентильное время первичного разбора не ухудшаются относительно 12 минут с учётом состава операций.
- Не увеличиваются необоснованные приостановки и жалобы в сопоставимом потоке.
- Все обязательные сигналы и операции сохраняются; отказ модели не удаляет операцию из очереди.

### 2.7. Вне объёма

- Автоматическое подтверждение схемы или отказ в проведении операции.
- Обучение классификатора «схема / не схема» на эскалациях как на готовом эталоне.
- Передача сырых операций и персональных данных внешнему API без отдельного положительного решения ответственных лиц.
- Замена внешней оценки риска клиента собственной итоговой оценкой банка или наоборот.
